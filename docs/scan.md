# 実際のスキャン（計画・一部実装）

> 「実装の順番」の 1〜7、9〜12 は実装済みです。今のアプリはこの端末のドライブを深さ優先で読み、SQLite（`lisa.db`）に残し、中身を BLAKE3 でハッシュして重複の一覧やスナップショットを作ります（`LISA_DUMMY=1` でダミーの木）。
> 保存するデータの形は [schema.md](schema.md)、ハッシュの考え方は [design.md](design.md) にあります。

本物のドライブを読んで、木に出し、ハッシュするまでに要るものと、その順番をまとめます。
Mac と Windows の両方で動かします。

## 先に直すもの: 木を「読んだところだけ」にする

今の UI はダミーの小さな木を前提にしていて、本物のドライブ（100 万〜300 万ファイル）では
持ちません。

- `FileTree` は全ノードを持ち、`Layouts` は全ノードの位置を一度に計算している。
- 位置が f32 のワールド座標の絶対値で、入れ子ごとに縮む。10 段くらいで精度が尽きる。本物の木は
  15〜20 段は普通にある。
- 起動時に全フォルダの画像を焼いている。

次のように変えます。

- 木は、開いているフォルダとその周り（親の一覧、隣、プレビューに見える 1〜2 段下）だけを持つ。
  残りは DB から必要なときに読む。
- 位置は、今の場面のフォルダを原点にした相対座標で計算する。開く・戻るたびに基準を付け替える。
- 画像は、見えるものだけを必要なときに焼き、ディスクに残す（schema.md の `folder_image`）。

## 永続ハッシュキュー

一覧を保存すると、新規・変更ファイルや集約待ちの既読フォルダが `hash_queue` に残ります。旧 DB は接続中のドライブごとに、最大 5,000 行・おおむね 20 ミリ秒ずつ補完します。完了後は再起動しても補完済みのドライブを再走査せず、切断中のドライブのキューは再接続まで保持します。

手動更新、表示中（優先度 10）、変更（20）、通常走査（30）の順に進みます。表示中のフォルダは直下を一段読み直して優先します。通常のバックグラウンド制限がかかるのは優先度 20・30 で、ブーストもこの範囲で効きます。ファイルは 4 スレッドで 1 MiB ずつ読み、DB の書き込みロックを持たずにハッシュします。確定した子から祖先へ順にフォルダの Merkle ハッシュを作ります。

中断した項目はそのまま残します。消えたファイルは親を再照合します。一覧が確定するまでキューに残して、再起動後も再照合またはハッシュできるようにします。ロック、ネットワークの一時断、タイムアウト、読取前後の属性変化は、一時失敗として 1 分、5 分、30 分、2 時間、6 時間、24 時間、24 時間の順に待ちます。8 回目の失敗、権限エラー、対象の種別不整合は `entry.error` に記録してキューから取り除きます。手動更新の一時失敗はエラーを表示し、初回の待機時間で自動再試行します。

待機中の仕事だけになったら進捗表示とブーストを終了します。次の期限まで 1〜60 秒間隔で待ち、期限に達したら再開します。`LISA_DEBUG_REMOTE=1` のコントロール口の状態には、接続中のドライブの即時実行可能件数、待機件数と次回期限が `hash_queue` に出ます。

## 組み立て

- **`lisa-core`**（Bevy に依存しない crate）に、ドライブの列挙、フォルダの読み取り、ハッシュ、DB を
  置きます。
- **`lisa-scan`**（CLI）で、スキャンだけを Mac と Windows で試せるようにします。Bevy のビルドを
  待たずに済みます。
- アプリ（Bevy）は `lisa-core` を呼ぶだけにします。
- スレッドは core が自前で持ちます（`std::thread`）。フォルダを読む係、ドライブごとのハッシュ係、
  DB に書く係（1 本）。何十分も I/O で止まる仕事なので、Bevy のタスクプールには入れません。
- UI と core はチャンネルでやりとりします。
  - UI → core: 今見ている場所、読んでほしい場所、止めて／続けて
  - core → UI: 子が読めた、ハッシュができた、状態が変わった、進み具合
- Bevy 側は、毎フレーム届いたものを決まった数だけ取り出して木に反映します。止まっている間は
  1 秒に 1 回しか描かないので、結果が届いたら winit の `EventLoopProxy` でイベントループを起こします。

## 読む順番と、裏で読むときの決まり

### 優先度

手動更新を最優先で処理します。永続キューでは、表示中フォルダの直下（10）、変更（20）、通常走査（30）の順にハッシュします。同じ優先度では期限、次に `entry_id` の順です。

### 裏で読む分（頼まれていない範囲）

ドライブ全体を裏で読みますが、ユーザーの邪魔をしないようにします。

- **止めてと言われたら、すぐ止める。** ファイルの途中でも、1 MiB 読むごとに止める合図を見ます。
  ハッシュの途中経過は捨て、あとで最初からやり直します。
- **ゆっくり読む。** OS に「後回しでいい I/O」と伝えます。
  - Mac: `setiopolicy_np(IOPOL_TYPE_DISK, IOPOL_SCOPE_THREAD, IOPOL_THROTTLE)`
  - Windows: `SetThreadPriority(THREAD_MODE_BACKGROUND_BEGIN)`（I/O の優先度も下がる）
  - それに加えて、1 秒あたりに読む量の上限を設定で持ちます。
- **ハードウェアが忙しそうなら止める。** CPU の使用率と、そのディスクの読み書きの量を数秒ごとに
  見て、しきい値を超えている間は休みます。電池で動いているときも休みます（設定で変えられる）。
- 手動更新と画面で見ているもの（優先度 10）は、この決まりにかかりません。すぐ読みます。

### ブースト

左下の進捗欄の「ブースト」を押すと、この画面を開いている Lisa の裏の走査と、その後の重複検出用
ハッシュを優先します。CPU が混んでいても進めます。Mac は作業スレッドのディスク I/O、Windows は
作業スレッドのバックグラウンドモードを通常に戻します。手動の一時停止、電池・ディスクの待機、読み取りの
上限、画面で見ているフォルダを先に読む順番はそのままです。

「通常に戻す」で通常の優先度と CPU 待機に戻ります。優先度を変えられなかったときは進捗欄に表示します。
通常モードで CPU 待機に入ったときは、ハッシュ中のファイルを開いたまま読み取り位置を保ち、再開すると続きから読みます。
走査からハッシュへ切り替わってもブーストは続き、作業が終わると解除されます。ほかの Lisa や次回起動には
引き継ぎません。

## 使う crate

| 用途 | crate | メモ |
|---|---|---|
| DB | `rusqlite`（`bundled`） | WAL。書くのは 1 スレッド、数千行ずつまとめてトランザクション |
| ハッシュ | `blake3` | 1 MiB ずつ読んで渡す。mmap は外付けを抜いたときに落ちるので使わない |
| 名前の正規化 | `unicode-normalization` | NFC |
| 端末 ID | `uuid`（v4） | |
| フォルダの読み取り | `std::fs::read_dir` を自前で回す | 1 段ずつ、優先度つきで読むので `walkdir` などは使わない |
| 忙しさ | `sysinfo` | CPU の使用率。ディスクの量は OS の API で |

| Windows の OS API | `windows` | ボリュームの情報、ファイル ID |

## ドライブの列挙と ID

### Mac

- `NSFileManager.mountedVolumeURLs` で一覧を取り、`NSURL` のリソース値でボリューム UUID、名前、
  容量、ファイルシステム、外付けか、大文字小文字を区別するかを取ります。
- 起動ディスクは「Macintosh HD」（システム）と「Macintosh HD - Data」（`/System/Volumes/Data`）に
  分かれていて、`/Users` などは firmlink で Data を指しています。`/` から下ると同じファイルを
  2 回数えるので、**ボリュームごとにそのマウント位置から読み、`st_dev` が変わったら下りません。**
  システム側は既定で読みません。

### Windows

- `GetLogicalDriveStringsW` で一覧、`GetVolumeInformationW` で名前、ファイルシステム、シリアル番号、
  大文字小文字の扱いを取ります。
- `\\?\Volume{GUID}\` の GUID は PC ごとに付く番号なので、ID には使いません。
- NTFS は 64 ビットのボリュームシリアル（`FSCTL_GET_NTFS_VOLUME_DATA`）を使います。

### Mac と Windows の両方につなぐ外付け

同じドライブでも、Mac と Windows で OS がくれる ID の形が違います（Mac は UUID、Windows は
シリアル番号）。次の順で同じドライブと見分けます。**ドライブにファイルは置きません。**

1. **FAT/exFAT**: Mac の UUID は、ボリュームのシリアル番号から MD5 で作られているようです
   （Apple の `msdos.util` のソース）。同じ作り方を Windows 側でもすれば、同じ UUID になる見込みです。
   **実機で確かめます。** ただし、同じメーカーのメディアはシリアルが同じことがあるので、容量と
   ファイルシステムも合わせて見ます。
2. 1 で決まらないときは、容量、ファイルシステム、名前、一番上のフォルダの中身（名前と大きさ）が
   合えば「同じドライブかもしれない」として、ユーザーに聞いてからまとめます。
3. それでもだめなときに限り、ドライブの一番上に小さな ID ファイルを置く案を残します（`.DS_Store`
   を置ける場所なら置いてよい、ただし置かずに済むほうがよい）。

`.DS_Store` 自体を ID に使うことはしません。Finder が自分の都合で書き換える（ウィンドウの位置を
変えただけで中身が変わる）、Windows だけで使うドライブには無い、Windows の人が消すことがある、
という理由で、同じドライブの印として当てにならないためです。

## 権限

- **Mac**: `~/Desktop`、`~/Documents`、`~/Downloads`、外付け、ネットワークは、初めて読むときに許可を
  聞かれます。`~/Library` の一部は**フルディスクアクセス**が要ります。アプリから頼むことはできない
  ので、読めるかを試して、だめならシステム設定のその画面を開く案内を出します。開発中の
  `cargo run` では、許可は起動した側（Terminal など）に付きます。配るときは署名した `.app` にします。
- **Windows**: `System Volume Information` や他のユーザーのフォルダは「アクセス拒否」になります。
- どちらも、読めなかったものは `status = 失敗`、`error = 権限` にして、UI で分かるようにします。

## リンク

- シンボリックリンクはたどらず、リンク先の文字列をハッシュします。Windows のジャンクションも同じ。
  ほかのリパースポイント（OneDrive のクラウドファイル、WSL のリンクなど）は種類を見て分けます。
- **ハードリンク**は、片方を消しても空きが増えないので、重複に数えません。ファイル ID が同じものは
  「同じファイルの別の名前」としてまとめます（Windows の `WinSxS` はハードリンクだらけ）。
- APFS のクローンは、ファイル ID は別でも中身を共有していて、消しても空きはほとんど増えません。
  見分けるのはあとの版で。

## クラウドにだけあるファイル

- **Mac**: ダウンロードしていないファイルには `SF_DATALESS` の印が付きます（`st_flags`）。起動時に
  `setiopolicy_np(IOPOL_TYPE_VFS_MATERIALIZE_DATALESS_FILES, IOPOL_SCOPE_PROCESS,
  IOPOL_MATERIALIZE_DATALESS_FILES_OFF)` を入れて、うっかり読んでもダウンロードが始まらないようにします。
- **Windows**: 属性（`FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS`、`RECALL_ON_OPEN`、`OFFLINE`）で
  見分けます。`read_dir` の時点で分かるので、開く前に判定します。

## 名前

- ディスク上の名前はバイト列で残します（Mac は不正な UTF-8、Windows は対になっていない UTF-16 が
  あり得る）。`name_nfc` は表示とハッシュ用です。
- フォルダのハッシュの並びは NFC の UTF-8 のバイト順。NFC で同じになる名前が並んだら、元のバイト列で
  順番を決めます。表示の並び（自然順など）は別にします。
- 大文字小文字はそのままハッシュに使います。`drive.case_sensitive` は、コピーで名前がぶつかる警告に
  使います。
- FAT/exFAT の更新日時は粗く、FAT はローカル時刻なので、時差のある場所でつなぐとずれます。
  「古いかも」になるだけで、ハッシュで正しく直ります。

## 速さの見積もり

- フォルダを読むだけなら、SSD で 1 秒に 10 万〜30 万件（200 万ファイルで数十秒〜数分）。
  Mac は 1 件ずつ `lstat` が要るので、遅ければ `getattrlistbulk` に替えます。
- ハッシュはディスクの速さで決まります。内蔵 SSD は 1 TB で 5〜10 分、外付け HDD は 1.5〜3 時間。
  HDD は並列にすると遅くなるので、並列数はドライブごとに持ちます（既定: 内蔵は数本、外付けは 1 本）。
  裏で読む分は、これよりずっとゆっくりです。
- DB は 200 万ファイルで 600 MB くらいの見込み。索引は `(drive_id, parent_id)`、`hash`、`size`。

## 監視（あとで）

- まずは、開いたときに読み直して、大きさと日時が違えば「古い」にします。
- 監視は `notify` で入れますが、取りこぼしの知らせが来ることがあるので、「このフォルダを読み直せ」
  というヒントとして扱います。
- Mac の FSEvents は、イベントの番号を覚えておけば、前回終わってから変わったところを起動時に
  もらえます。Windows の USN ジャーナルも同じことができますが、管理者権限が要ります。

## schema.md に足すもの

実装するときに一緒に直します。

- `entry.name` をバイト列（BLOB）に。
- `entry.kind` に `other`（ソケットなど。記録だけして読まない）。
- `entry.error` の種類（権限 / 見つからない / 読み取りエラー / クラウド）。
- `entry.nlink`（ハードリンクの数）。
- `drive` に OS ごとの ID（Mac の UUID、Windows のシリアル）を別の列で。
- 読む場所と除外の表。既定の除外は、Mac の `.Spotlight-V100`、`.fseventsd`、`.Trashes`、
  `.DocumentRevisions-V100`、`/private/var/vm`、Windows の `pagefile.sys`、`hiberfil.sys`、
  `swapfile.sys`、`System Volume Information`、`$Recycle.Bin`。
- （監視のとき）`drive` に FSEvents の番号 / USN の位置。

## 実装の順番

それぞれ PR 1 つくらいの大きさです。

1. **crate を分ける**: `lisa-core` と `lisa-scan` を作る。UI は変えない。フォルダを 1 段読むところ
   （`listing.rs`）まで入れて、CLI で試せるようにする。
2. **ドライブの一覧**: Mac と Windows で列挙して、`lisa-scan` で出す。外付けの ID が Mac と Windows で
   そろうかを、ここで実機で確かめる。
3. **木を「読んだところだけ」にする**: 相対座標、必要なところだけの配置、見えるものだけ焼く。
   まだダミーのデータで確かめる。木そのもの（`FileTree`）を、子をまだ読んでいないフォルダを
   持てる形にするのは 4 で、読む処理と一緒にやる。
4. **ドライブとフォルダを本物に**: 端末 > ドライブを本物にし、開いたフォルダを裏で 1 段ずつ読んで
   出す。除外、リンク、クラウド、権限のエラーをここで扱う。今はダミーの `LoadState`（`model/tree.rs`）を、
   読んだ結果で付けるようにする。
5. **SQLite に残す**: `device`、`drive`、`entry`。次に起動したら DB から出して、開いたら読み直す。
6. **ファイルのハッシュ**: 見ている場所から近い順に。待ち行列も DB に。
7. **フォルダのハッシュ**: Merkle、`tree` の表、古い / 読込済。
8. **画像キャッシュをハッシュで**: ディスクに残して、起動してすぐ出せるように。
9. **重複の一覧**: ハッシュでまとめる。ハードリンクは分ける。
10. **裏で全体を読む**: 止める、ゆっくり読む、忙しいときは休む。
11. **監視**。
12. **スナップショット**。
