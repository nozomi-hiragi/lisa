# カタログ

> 実装しました（`crates/lisa-core/src/catalog.rs` と `catalog/`、`crates/lisa-mcp/src/catalog.rs`、
> `src/catalog.rs`、`src/ui/catalog.rs`、`src/render/tag.rs`）。計画から変えたところは、各節と最後の
> 「実装で決めたこと」にあります。保存するデータの形は [schema.md](schema.md)、ハッシュの考え方は
> [design.md](design.md) にあります。

カタログは「このアプリのフォルダは、こういう形をしている」という型を書いたファイルです。
フォルダやファイルの名前、種類、中身をパターンで書いておくと、Lisa が木の中から当てはまる
フォルダを見つけて、どのアプリのものかを画面に出します。
型を書くのも、型に当たらないフォルダを仕分けるのも、LLM に MCP から任せられるようにします。

## 考え方

- **カタログはファイルが元です。** 1 つの型を 1 つの TOML ファイルにして、フォルダにまとめて
  置きます。リポジトリに入れて、差分を読んだり PR でレビューしたりできる形にします。
- **カタログには PC ごとの情報を書きません。** ドライブ ID、マウントしたパス、ユーザー名などは
  入れず、どの PC でも同じファイルで当たるようにします。
- **1 か所ごとの仕分けは DB に残します。** 「このフォルダはこのアプリ用」という、型にならない
  1 か所ものは PC ごと・ドライブごとの話なので、カタログではなく `lisa.db` に持ちます。
- **当たったかどうかの結果は DB に覚えるだけです。** カタログのファイルを変えたら、当て直します。
- カタログは見分けて見せるためのものです。ファイルを動かすのは整理（[organize.md](organize.md)）で、人が許可したときだけです。

## 置き場所

- 組み込みのカタログは、このリポジトリの `catalogs/` に置き、アプリと一緒に配ります（`lisa-core` の
  `build.rs` で実行ファイルに埋め込む。`lisa_update` で実行ファイルを入れ替えるだけで配れるように）。
- ユーザー用のカタログのフォルダは、データのフォルダの `catalogs/` です（`lisa_catalog_save` の既定の書き先）。
- 設定（`settings.json`）の `catalog_dirs` で、カタログを読むフォルダを足せます（複数可。設定の
  ポップアップには出さず、手で書く）。自分用のカタログを別の場所や別のリポジトリに置くときに使います。
- 読む順は、組み込み → ユーザー用のフォルダ → `catalog_dirs` の順です。
- 読むフォルダのファイルが変わったら（追加・変更・削除）、読み直して当て直します。
- 同じ `id` の型が 2 つあったら、後に足したフォルダの方を使います（組み込みを自分用で上書きできる）。

## ファイルの形

```toml
# catalogs/unity.toml
id   = "unity-project"        # 型の ID。ファイルの間で重ならないもの
name = "Unity プロジェクト"      # 画面に出す名前
app  = "Unity"                # どのアプリのものか（同じアプリの型をまとめるのに使う）
color = "#7fb4ff"             # 耳の札の色（省略すればアプリ名から決める）
label = "Unity {ver}"         # 札に書く文字。{名前} は中身の正規表現で取った値

# このフォルダの中に、これが全部あれば当たり
[[match]]
path = "Assets/"

[[match]]
path = "ProjectSettings/ProjectVersion.txt"
content = 're:m_EditorVersion: (?<ver>\S+)'

# これがあれば外れ（任意）
[[exclude]]
path = "package.json"

# 当たったフォルダの中の役割
[[part]]
path = "Library/"
role = "cache"

[[part]]
path = "Temp/"
role = "cache"

[[part]]
path = "Assets/"
role = "data"
```

- `match` は全部そろったら当たり、`exclude` が 1 つでもあれば外れです。
- `match` が何も無い型は作れません（全部のフォルダに当たってしまうため）。
- 全部の `match` の 1 段目が `**` の型も作れません（候補を名前で絞れず、全部のフォルダを確かめることになるため）。
- `path` は当たるフォルダから見た相対パスです。`/` で終われば「フォルダ」、終わらなければ
  「ファイル」です。区切りは OS によらず `/` です。

### 名前の書き方

- 基本はふつうのパターン（glob）です。`*` は 1 段の中の何でも、`**` は何段でも、`?` は 1 文字、
  `{a,b}` はどちらか、です（例: `*.uproject`、`**/*.blend`）。
- 先頭に `re:` を付けると、その段の名前を正規表現で書けます（例: `re:^Steam(Library)?$/`）。
  パターンの各段で、glob と正規表現を混ぜて書けます。
- 名前は NFC にそろえてから比べます。Mac（NFD）と Windows で同じに当たるようにするためです。
- 大文字小文字は区別しません。区別したいときは、その `match`・`exclude`・`part` に `case = true` を
  付けます（段ごとではなく、その項目のパターン全体にかかります）。
- `**` が下りるのは 8 段までです。
- 知らないキーはエラーにします（打ち間違いに気づけるように）。

### 中身の書き方

ファイルを指した `match` には、中身の条件を付けられます。

| キー | 意味 |
|---|---|
| `content = 're:…'` | ファイルの先頭（既定 64 KiB）を UTF-8 として読み、正規表現が当たれば当たり。名前付きの組 `(?<名前>…)` で取った値は `label` に使える |
| `content_bytes = "hex:…"` | 先頭のバイト列がこれで始まれば当たり（マジックナンバー） |
| `hash = "blake3:…"` | 中身のハッシュがこれなら当たり（特定の exe などを決め打ちするとき） |
| `size = "<10MiB"` | 大きさの範囲（`<`、`>`、`a..b`） |
| `head = "1MiB"` | 読む先頭の長さを変える（上限 1 MiB） |

- 中身を読むのは、名前と形がもう当たった候補のファイルだけです。全部のファイルを読むと重いためです。
- クラウドにだけあるファイル（`cloud_only`）は読みません（読むとダウンロードが始まるため）。中身の
  条件は「分からない」とし、名前と形だけで当たっていれば「たぶん当たり」として出します。
- 結果は「ファイルのハッシュ × 条件」で覚えます。中身が変わらない限り読み直しません。

### 役割（`role`）

| 役割 | 意味 |
|---|---|
| `data` | ユーザーが作ったもの。消すと戻らない |
| `config` | 設定 |
| `cache` | 消しても作り直せるもの（ビルドの結果、一時ファイル、ダウンロードの置き場） |
| `install` | アプリ本体やゲームの中身など、入れ直せば戻るもの |
| `log` | ログ |

- 役割は画面の描き方と、重複の並べ方に使います（下を見てください）。
- 役割を書かない中身は、何も付きません。

### 入れ子

- 型の中に別の型が当たることがあります（例: Steam のライブラリの中のゲームのフォルダ）。どちらも
  出します。外側の `part` の役割は、内側に当たった型の役割より弱いとします。
- 同じフォルダに 2 つの型が当たったら、どちらも一覧に出します。札は 1 つだけで、仕分け → 中身から
  札の文字を取った型（Rust のクレート名など）→ 型の名前だけの札（Git リポジトリなど）の順に選びます。
- ほかの当たりの `cache` の中にある当たりは出しません（`node_modules` の中の 1 つ 1 つのパッケージなど。
  作り直せるものの中なので、並べても役に立たない）。`install` の中（Steam のゲームなど）は出します。

## 1 か所ごとの仕分け

型にならないフォルダは、1 か所ずつ「このアプリ用」と仕分けられます。

- 画面では、カタログのパネルの「このフォルダの仕分け」で、今開いているフォルダにアプリを選んで付けます
  （型と仕分けに出てくるアプリから選ぶ。役割とメモは MCP の `lisa_assign` から）。外すのも同じ所です。
- `lisa.db` の `assignment` に残します（下を見てください）。ドライブ ID とパスで指します。フォルダの
  ハッシュは中身で変わるので、指す先には使いません。
- フォルダが動いたら、`file_id`（inode など）で追いかけます。追えなくなったら「見失った」として
  一覧に残し、消しはしません。
- 仕分けは型と同じく、アプリ名と役割を持てます。型の当たりより仕分けを先にします（人や LLM が
  決めたものなので）。

## 当て方

- 型ごとに、1 段目が `**` でない `match`（なるべく文字そのもの）を 1 つ選び、その 1 段目の正規表現を
  まとめた `RegexSet` で `entry` を 1 回なめて、名前の当たった行の親を候補にします。候補ごとに残りを確かめます。
- 深いパス（`a/b/c`）の `match` は、その段のフォルダが読めてから確かめます。読めるまでは「確かめ中」
  （`pending`）です。読まないフォルダ（別のボリューム、クラウドにだけあるフォルダ）は空として扱います。
- 中身を読むのは、名前と形が全部そろった候補だけです。アプリの裏のスレッド（`src/catalog.rs`）が
  そのまま読みます（`hash_queue` はまだ無いので、`reason = catalog` は使っていません）。
- 当て直すのは、カタログのファイル（名前・大きさ・更新日時）か DB の状態（ドライブごとの一番上の
  ハッシュ、`entry` の変更、ドライブの付け外し）が変わったときです。5 秒ごとに見て、続けては 3 分より短い
  間隔で当て直しません。
- **全体を当て直すのは、起動して最初・カタログのファイルが変わったとき・ドライブを付け外ししたとき・
  失敗のあと・変わったフォルダが 2048 を超えたとき（走査の直後など）だけ**です。ふだんは、`entry` の
  トリガーが同じトランザクションで `catalog_dirty` に書いた「変わったフォルダ」と、その祖先だけを当て直します。
  「確かめ中」「たぶん」の当たりは毎回当て直します。トリガーはハッシュの列を見ません（中身が変われば大きさか
  更新日時も変わるため）。全体でも 512 行ずつ読み、読み取りのトランザクションを長く持ちません。
- 当たりの大きさと未分類のフォルダは、手元に持っている「フォルダごとの直下の大きさと子フォルダ」から求めます
  （フォルダの数の分だけメモリに持つ）。以前は当たりごとに下を全部 DB から読んでいて、実データ（当たり 423 か所）で
  1 回 52〜133 秒かかっていました。いまは全体で 7〜11 秒、ふだんは 1 秒前後です。
- 失敗したら、5 秒から倍ずつ延ばして（最大 3 分）全体を当て直します。
- `lisa-scan catalog [--dir <フォルダ>]... [--drive <id>] [--only <型>] [--near]` で、DB に書かずに当たりと
  惜しい候補を出せます。

## 画面

- 型か仕分けに当たったフォルダは、耳のすぐ右に札を付けます。札にはアプリの色と `label` を書きます
  （耳は本体の左端から始まるので、左には置けない）。耳の右に入らなければ、本体の左上（耳のすぐ下）に掛けます。
- 中の `cache`、`install`、`log` は少し暗く描きます。`data` はそのままです。
- 札と暗い膜は、重複の印と同じく本物の場面にだけ描き、フォルダの画像には焼きません（画像の鍵を変えずに済むように）。
- 右から出るパネル（重複のパネルと同じ出方で、メインの表示を縮めて場所を空けます）に、アプリごと・
  型ごとの当たりの一覧と、合計の大きさを出します。選ぶと木の上で光り、押すとそこへ寄ります。
- 「どの型にも当たらない大きなフォルダ」の一覧も同じパネルに出します。仕分けの入口です（大きさは
  当たったフォルダの分を除いたもの。1 GiB 以上を含む一番深いフォルダを 30 個）。
- パネルは、メニューバーの「カタログ」で開け閉めします。重複の一覧とは同時に開きません。外から動かす口
  （`lisa_core::remote`）の `catalog` でも開けます。

## 重複の一覧との関係

- `cache` と `install` の中の重複は、一覧の後ろに回します（消しても作り直せるものだから）。
- 型ごとに「この型の中は重複の一覧に出さない」も選べます（設定の `catalog_hide_duplicates` に型の ID を
  並べる。ポップアップには出さない）。
- 同じ型に当たったフォルダどうしは、カタログのパネルでアプリごと・型ごとにまとめて並べます。

## 複数の PC

- LAN でつながった Lisa どうしで、カタログのファイル（組み込みと、設定で足したもの）を見せ合います。
  相手にしか無い型は、相手の木を見るときだけ使います。自分のカタログに取り込むのはユーザーが選びます。
- 相手の木への当てはめは、相手の Lisa がやって結果を返します。中身の条件はファイルのある PC でしか
  読めないためです。
- こちらは、ペアリングした相手の `lisa_catalog_matches`（`parts: true`）と `lisa_catalogs`
  （`include_text: true`）を 1 分ごとに読み、相手の木に札と暗い膜を描きます。相手にしか無い型は、パネルで
  押したときだけ、ユーザー用のカタログのフォルダに取り込みます（同じ名前があれば書かない）。
- 仕分け（`assignment`）は、ドライブの持ち主の端末の DB にあります。ドライブが別の PC に移ったら、
  前の端末の仕分けを、つながったときに引き継ぎます（まだ作っていません）。

## MCP

LLM に型を書かせたり、フォルダを仕分けさせたりするための道具を `lisa-mcp` に足します。
書き込むのは、カタログのファイル（読むフォルダの中だけ）と仕分けだけです。ユーザーのファイルには
触りません。

| 道具 | 中身 |
|---|---|
| `lisa_catalogs` | 読んでいる型の一覧（ID、名前、アプリ、ファイルの在りか、当たった数、読めなかったときの理由） |
| `lisa_catalog_matches` | 型ごと・アプリごとの当たったフォルダ（端末、ドライブ、パス、大きさ、`label`） |
| `lisa_unclassified` | どの型にも仕分けにも当たらない大きなフォルダ（大きさ順、場所で絞れる） |
| `lisa_outline` | フォルダの「形」の要約。上から数段の名前、拡張子ごとの数と大きさ、よく出る名前、小さなテキストの先頭（長さの上限つき）、すでに当たっている型 |
| `lisa_catalog_test` | 書きかけのカタログ（TOML の文字列）を保存せずに DB に当て、当たったフォルダと、惜しく外れた候補（どの `match` で外れたか）を返す |
| `lisa_catalog_save` | カタログのファイルを書く（新規・上書き）。書く前に `lisa_catalog_test` と同じ確かめをして、形が壊れていれば書かない |
| `lisa_assign` / `lisa_unassign` | 1 か所の仕分けを付ける・外す |

LLM の流れの例:

1. `lisa_unclassified` で、仕分けられていない大きなフォルダを取る。
2. `lisa_outline` で中の形を見て、どのアプリのものか当てる。
3. 同じ形が他にもありそうなら型を書き、`lisa_catalog_test` で当たり外れを見ながら直す。
4. `lisa_catalog_save` で保存する。リポジトリの `catalogs/` に置いたものは、あとで PR にする。
5. 型にならない 1 か所ものは `lisa_assign` で仕分ける。

## 保存するデータ（DB）

カタログそのものは DB に入れません。DB には当てた結果と仕分けだけを持ちます。

### catalog_match（型の当たり）

| 列 | 中身 |
|---|---|
| `entry_id` | 当たったフォルダ |
| `catalog_id` | 型の ID |
| `catalog_rev` | 当てたときの型のファイルのハッシュ。今と違えば当て直す |
| `state` | `match`（当たり） / `maybe`（中身が分からないが形は当たり） / `pending`（確かめ中） |
| `captures` | 中身の正規表現で取った値（JSON） |
| `matched_at` | 当てた日時 |

### content_check（中身の条件の結果）

| 列 | 中身 |
|---|---|
| `hash` / `algo` | ファイルの中身のハッシュ |
| `rule` | 条件のハッシュ（`content` などの文字列と読む長さから作る） |
| `hit` | 当たったか |
| `captures` | 取った値（JSON） |

### assignment（1 か所の仕分け）

| 列 | 中身 |
|---|---|
| `id` | 行の番号 |
| `drive_id` | どのドライブか |
| `path` | ドライブの一番上から見たパス（NFC） |
| `file_id` | 付けたときの OS のファイル ID（動いたときに追うため） |
| `app` | アプリ名 |
| `role` | 役割（任意） |
| `note` | メモ（任意） |
| `by` | 付けたのは `user` か `mcp` か |
| `created_at` / `lost_at` | 付けた日時、見失った日時 |

## 実装の順番

1. `lisa-core` にカタログの読み込み（TOML）と当てはめ（名前と形だけ）を置く。`lisa-scan catalog`
   で、ドライブにどの型が当たるかを CLI で試せるようにする。
2. 組み込みの型をいくつか `catalogs/` に置く（Unity、Xcode の DerivedData、Steam のライブラリ、
   node_modules など）。
3. 中身の条件（`content`、`content_bytes`、`hash`、`size`）と `content_check`。
4. MCP の道具（読むもの → `lisa_catalog_test` → 書くもの）。
5. 画面: 耳の札、役割で暗く描く、右のパネル。
6. 1 か所の仕分け（`assignment`）と、画面のメニュー。
7. 重複の一覧との連動。
8. LAN でカタログと当たりを見せ合う。

## 実装で決めたこと

計画に無かったこと、計画と変えたことです。

- **全部の `match` が `**` で始まる型はエラー**にしました（候補を名前で絞れないため）。
- **`case = true` は項目ごと**です（計画では段ごと）。
- **`node_modules` の中のパッケージのように、ほかの当たりの `cache` の中の当たりは出しません。**
  自分の DB で Node.js の当たりが 1414 か所から 292 か所になりました。
- **札は耳の右**（入らなければ本体の左上）。計画では耳の左でした。
- **札と暗い膜は画像に焼きません。** 本物の場面にだけ描きます。
- **当て直しは全部の型をまとめて**行います（変わった型だけにはしていない）。ふだんは変わったフォルダだけです
  （上の「当て方」）。中身の読み込みは
  `hash_queue` ではなく、カタログの裏のスレッドが直接読みます。
- **カタログの裏のスレッドも DB に書きます**（`catalog_match`、`content_check`）。読む係とは別の
  つなぎで、短いトランザクションにしています（`busy_timeout` で待つ）。仕分けは画面と MCP から書きます。
- **画面での仕分けは、今開いているフォルダに、アプリを選んで付ける形**です（文字の入力欄が無いため）。
  役割とメモは MCP の `lisa_assign` から付けます。
- **外から動かす口に `catalog`（パネルの開け閉め）と `capture`（アプリ自身で窓を撮って、データの
  フォルダの `screenshots/<name>.png` に残す）を足しました。** 画面収録の許可が無くても見た目を確かめられます。
- **LAN の相手も `lisa_catalog_save` と `lisa_assign` を呼べます**（合言葉かペアリングの鍵が要る）。
  書けるのはカタログのフォルダの中と `assignment` だけです。
- まだのもの: ドライブが別の PC に移ったときの仕分けの引き継ぎ、型ごとの当て直し、パネルからの役割の付け替え、
  LAN の相手の当たりの一覧から相手の木の場所へ飛ぶこと。
